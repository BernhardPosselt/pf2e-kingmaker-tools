# Random Encounter & Rumor Curator Implementation Plan

> **Status:** Draft — pending review
> **Date:** 2026-06-01

---

## Executive Summary

This plan describes the **Random Encounter & Rumor Curator** for the pf2e-kingmaker-tools module (roadmap item #11). The system extends the existing random encounter flow with a category-based routing system. Instead of a single proxy table deciding "Creature vs. nothing," a category proxy table routes to category-specific tables (Combat, RP, Rumor, Merchant, Disease, Faction, Weather, Lore). A new `EncounterPreviewDialog` (GM-only, following the `ConfirmWatchApplication` pattern) lets the GM preview, accept, reject, or reroll encounters before they are posted to chat. Rumors generated by encounters can be converted into quests.

**Key capabilities:**

- **8 encounter categories:** Combat, RP, Rumor, Merchant, Disease, Faction, Weather, Lore
- **Category-based routing:** Category proxy table routes to per-category roll tables (configured per-region)
- **GM preview dialog:** Accept, reroll, or reject encounters before they hit chat; convert rumor hooks to quests
- **Hex state filtering:** Optionally suppress Combat encounters in claimed+cleared hexes
- **Rumor-to-quest pipeline:** Rumors with quest hooks can generate `CampaignQuest` records stored in `KingdomData`
- **Configurable weights:** Per-category relative weights (0-100) control encounter frequency distribution

## Non-goals

- Do NOT implement the full quest/event generator (roadmap item #2, separate feature). Rumor-to-quest conversion creates simple quest records but the full `QuestGenerator` engine is out of scope.
- Do NOT implement campaign clock integration. Quest due dates from rumors are not clock-integrated.
- Do NOT add auto-generation of encounters on kingdom turn. The encounter curator is GM-triggered via the camping sheet.
- Do NOT implement homebrew profile import/export (roadmap item #9, separate feature).
- Do NOT add pacing/balance alert thresholds (roadmap item #13, separate feature).
- Do NOT rename or refactor the existing `proxyRandomEncounterTableUuid` field — the new `encounterCategoryProxyTableUuid` is additive.

### CategoryWeights (commonMain)

```kotlin
package at.posselt.pfrpg2e.camping

data class CategoryWeights(
    val combat: Int = 30,
    val rp: Int = 15,
    val rumor: Int = 15,
    val merchant: Int = 10,
    val disease: Int = 5,
    val faction: Int = 10,
    val weather: Int = 10,
    val lore: Int = 5,
) {
    val total: Int get() = combat + rp + rumor + merchant + disease + faction + weather + lore

    fun normalized(): Map<EncounterCategory, Double> {
        val t = total.toDouble().coerceAtLeast(1.0)
        return mapOf(
            EncounterCategory.COMBAT to combat / t,
            EncounterCategory.RP to rp / t,
            EncounterCategory.RUMOR to rumor / t,
            EncounterCategory.MERCHANT to merchant / t,
            EncounterCategory.DISEASE to disease / t,
            EncounterCategory.FACTION to faction / t,
            EncounterCategory.WEATHER to weather / t,
            EncounterCategory.LORE to lore / t,
        )
    }
}
```

## Migrations

Migration27 (`Migration27.kt`) adds all new fields with safe defaults. This is a **purely additive** migration — no existing fields are modified or removed.

### Migration steps

1. Read current `CampingData` — add new fields with defaults (see table above)
2. Read current `RegionSetting` per region — add `categoryRollTableUuids = {}`, `suppressEncountersOnClearedHex = false`
3. Read current `KingdomData` — add `rumorGeneratedQuestIds = []`
4. Write back with `migrationVersion = 27`

### Backward compatibility

- Legacy `proxyRandomEncounterTableUuid` field is NOT removed — it continues to work for "Creature vs. nothing" rolls
- `encounterCategoryProxyTableUuid` is a separate, additive field
- When `encounterCategoryProxyTableUuid` is null, the system falls back to legacy proxy table behavior
- All new collection fields default to empty lists/maps — no null safety issues

### Rollback

No destructive changes to existing data. Rollback is simply not persisting the migration version.

### appFlag keys

| Key | Shape | Purpose |
|-----|-------|---------|
| (existing camping flags) | Extended with new fields | New fields stored in existing camping data structure |

```kotlin
fun shouldSuppressCombat(camping: CampingData, kingdomData: KingdomData): Boolean {
    if (!camping.filterByHexState) return false
    // Check if current region's hex is claimed and cleared in kingdom data
    return kingdomData.isCurrentHexClaimedAndCleared(camping.currentRegion)
}
```

## Risks & Open Questions

### Risks

1. **Hex state access from camping context.** The camping sheet needs to read kingdom actor hex state to determine if the current hex is claimed+cleared. This crosses the camping→kingdom boundary. **Mitigation:** Follow the existing pattern where `CampingSheet` accesses the kingdom actor via `game.actors`. The `KingdomData` hex state methods are already tested in `HexStateTest`. The hex state check is a read-only operation that doesn't modify kingdom data.

2. **Transient fields not persisted.** `lastEncounterCategory` and `lastEncounterResult` are transient (not persisted to the DB). If the GM closes the preview dialog without accepting/rejecting, the encounter is lost. **Mitigation:** This is intentional — the preview dialog is a transient workflow. The GM must explicitly accept or reject. If they close the dialog, they can re-roll.

3. **Per-region category table configuration complexity.** 8 categories × N regions means many table dropdowns. **Mitigation:** The category columns in region config use the same pattern as the existing roll table column. Only populate tables for categories the GM actually uses; null means "use default."

4. **Rumor data stored in session state vs. persisted.** Rumors are stored in `CampingData.rumors` which is persisted. This means rumors accumulate across sessions. **Mitigation:** Rumors are lightweight data objects. A cleanup pass can be added when the camping session ends (existing hook: daily preparations reset).

5. **Legacy proxy table coexistence.** Having both `proxyRandomEncounterTableUuid` (legacy) and `encounterCategoryProxyTableUuid` (new) could confuse GMs. **Mitigation:** When `encounterCategoryProxyTableUuid` is set, it takes priority. The legacy field is hidden in the UI when the new field is populated. Clear i18n help text explains the relationship.

### Open Questions

1. **Should merchant stock be persistent or regenerated each encounter?** Merchant stock is currently designed as session state that persists for the camping session but resets when the session ends. — **Decision:** Session-stock model. Stock is generated when the merchant is first encountered and persists for the remaining camping session. A "restock" hook can be added to the daily preparations flow later.

2. **Should the GM be able to manually select a category instead of rolling?** This would allow GMs to force a specific encounter type. — **Decision:** Not in v1. The preview dialog's reroll mechanism gives the GM enough control. A "force category" dropdown can be added to the preview dialog in a future iteration.

3. **Quest template JSON files: campaign-scoped or module-scoped?** Quest templates for rumor-to-quest conversion need to come from somewhere. — **Decision:** Module-scoped JSON files in `data/encounter-rumor-quest-templates/` following the existing `data/events/` pattern. This keeps them data-driven and easily extensible.

4. **Should there be a limit on rumors stored in CampingData?** Rumors accumulate in `CampingData.rumors` across sessions. — **Decision:** No hard limit in v1. Rumors are small data objects. If accumulation becomes a problem, a cleanup pass during daily preparations can trim rumors older than N sessions.
